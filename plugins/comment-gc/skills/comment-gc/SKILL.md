# Comment GC

Comments accumulate. One session writes `// switched to a Map for O(1) lookup`, the next
adds `// note: the array version is gone now`, a third explains what the loop does, and
after a dozen sessions the comments describe the file's history instead of its present.
Nobody deletes them, because deleting someone else's note feels risky.

This skill does the collecting: **delete what stopped being true or never earned its place,
compress the rest to its point, touch no code.**

The hard constraint is the whole value proposition: **the code must come out identical once
comments and whitespace are removed** — not "mostly unchanged", identical, and proven with
`scripts/code_guard.py` before you report. A comment cleanup that quietly renames a variable
is a cleanup nobody will ever run again.

## Arguments

| Input | Target |
|---|---|
| *(nothing)* | Files changed on this branch vs. its merge base with the default branch |
| a path, glob, or directory | Exactly those files |
| `--staged` | Files staged in the index |
| `main..HEAD` or any rev range | Files changed in that range |

## 1 — Resolve the file list

```bash
git symbolic-ref --quiet --short refs/remotes/origin/HEAD   # default branch
git merge-base origin/<default> HEAD
git diff --name-only <base>...HEAD
```

Drop, before reading anything: lockfiles; generated files (`Code generated by`, `@generated`,
`DO NOT EDIT`); vendored and third-party trees; minified bundles; snapshots; data and
markup-only files with nothing to clean. Say which files you dropped and why — silently
skipping a file the user expected you to handle is worse than skipping it out loud.

If nothing survives, or the surviving files have healthy comments, **say so and stop**.
"Nothing worth collecting here" is a correct and common outcome. The failure mode of this
skill is manufacturing work to look useful.

## 2 — Snapshot before you touch anything

```bash
python3 <skill>/scripts/code_guard.py save <scratch>/comment-gc-snapshot <files...>
```

This is the before-image that step 5 compares against and, when something goes wrong,
restores from. It works whether or not the working tree was clean, which `git diff` alone
does not.

## 3 — Judge each comment

Read the code, not just the comments. Whether a comment is garbage or load-bearing is a
fact about the code underneath it, and you cannot tell them apart from the comment text.

**The razor — delete the comment in your head and ask what the next person gets wrong.**

- Nothing → delete it.
- They'd have to re-derive something the author already learned the hard way, walk into a
  trap, or undo something deliberate → keep the fact, compress the words.
- They'd misread the code → the comment is either wrong (delete) or the code is unclear
  (leave both alone; fixing that is a code change, and code is off limits here).

**The second question — where else does this information live?** Anything already carried by
the code, the types, the tests, `git log`, an ADR, or the issue tracker is a duplicate, and
duplicates are exactly what goes stale. This project keeps architectural rationale in ADRs
and other docs, so a comment re-telling a design decision is not the only copy.

### Delete

- **Stale** — describes behavior the code no longer has, arguments that no longer exist,
  branches that were removed.
- **History and narration** — "previously we used X", "changed from A to B", "as requested",
  "after review feedback", dates, session and PR references, "the old helper is gone".
  `git log` and `git blame` hold this, and hold it accurately.
- **Commented-out code** — old implementations, dead branches, debug prints. It is a comment,
  so it is in scope, and version control has a better copy. (A deliberate usage example or a
  config template is not this — keep those.)
- **Restatement** — `i += 1  // increment i`; a docstring whose only sentence is the function
  name in prose; a header that names the class directly beneath it.
- **Conversational residue** — first person, hedging, "let's", "for now", notes addressed to
  the user of a chat session rather than to a reader of the file.
- **Duplicates** — the same explanation on the function, at the call site, and inside the
  loop. Keep the copy nearest what it explains.
- **Empty scaffolding** — doc blocks with no content, `TODO: implement` above a finished
  implementation, banner comments that restate the file's structure.

### Keep verbatim — never edit these

They are load-bearing to a machine or to the project's legal posture, and their wording is
part of their function:

- Tool directives: `eslint-disable*`, `@ts-ignore`, `@ts-expect-error`, `# type: ignore`,
  `# noqa`, `# pylint:`, `# fmt: off`, `# pragma: no cover`, `istanbul ignore`,
  `prettier-ignore`, `//go:build`, `//go:generate`, `#pragma`, `@SuppressWarnings`,
  shebangs, encoding declarations, editor modelines.
- License headers, copyright lines, SPDX identifiers.
- `Code generated ... DO NOT EDIT` markers.

When you meet an unfamiliar marker-shaped comment — a `@`, `#`, or `!` prefix, an odd
capitalization, something that reads like a flag rather than a sentence — assume a tool reads
it and leave it alone. The cost of keeping one machine comment is a line; the cost of
deleting one is a broken build nobody connects to a comment cleanup.

### Keep the fact, compress the words

- **The why behind non-obvious code**: the workaround and the bug it dodges, ordering
  constraints, a measured performance reason, a spec or protocol requirement, a security
  consideration, "must stay in sync with X".
- **Links** — issue, spec, RFC, vendor bug URLs. You cannot verify what is on the other end,
  and the URL is the cheapest, densest part of the comment. Shorten the prose, keep the link.
- **TODO / FIXME / HACK with real content**, especially with a ticket reference. Trim the
  prose; keep the marker, the subject, and the reference. Deleting a TODO silently converts
  an open loop into a closed one.
- **Contracts in doc comments** — parameters, return values, raised errors, units, valid
  ranges, side effects, async or thread constraints, deprecations, and the `@param` /
  `@returns` / `@throws` tags a doc generator reads. A caller who cannot see the body still
  needs these. Cut the essay around them, not them.
- **Non-obvious domain meaning** — where a magic constant came from, what a dense regex is
  for, an encoding or timezone quirk.

### How to compress

- Keep each comment in the language it was written in. A comment in Korean, Japanese, or
  German comes out shorter in that same language — you were asked for less text, not for a
  translation, and the team that wrote it should still recognize its own words.
- Keep the original comment syntax, indentation, and placement.
- Never assert something the original did not. Summarizing is allowed, inferring is not. If a
  sentence is too vague to compress without guessing, leave it as it is.
- Cut the wind-up and keep the payload: "The purpose of this method is to" and "This
  function is responsible for" carry no information.
- **Do not add comments.** Not even good ones. A file that needs a comment you would have to
  write is a code problem, and this skill does not touch code.

Three examples of the whole judgment, end to end:

```python
# Before — 2024-03-11: switched from split() to a regex because the old version
# broke when the input had tabs in it. Reviewed by the team and agreed this is
# the right approach for now. Takes a raw line and returns its fields.
parts = re.split(r"\s+", raw.strip())

# After — the history is in git; the regex explains itself.
parts = re.split(r"\s+", raw.strip())
```

```typescript
// Before
/**
 * Formats a price for display. Note that I originally tried using
 * Intl.NumberFormat here, as requested in the review, but it turned out that
 * Safari 16 rounds half-to-even which broke two of our tests, so after some
 * back and forth we decided to do the arithmetic by hand instead.
 * See https://bugs.webkit.org/show_bug.cgi?id=1234
 * @param n - the amount
 */

// After — the trap survives, the story does not.
/**
 * Formats a price. Hand-rolled: Intl.NumberFormat rounds half-to-even in
 * Safari 16 (https://bugs.webkit.org/show_bug.cgi?id=1234).
 * @param n - the amount
 */
```

```go
// Before — the retry loop is here because the way we did this before had
// problems. We settled on 3 attempts as requested in review, and it could be
// pulled out into config later if anyone ends up needing that. Note that the
// payment gateway returns intermittent 502s under load (INFRA-441).

// After — the fact and the ticket survive; the deliberation does not.
// The payment gateway returns intermittent 502s under load, so retry 3 times
// (INFRA-441).
```

Had the original been written in Korean or Japanese, the shortened version would be in that
language too — the same sentence, minus the deliberation.

### Decide yourself; ask only where it is genuinely a coin flip

Handle the clear cases and keep moving — a cleanup that stops to ask about every line is
worse than no cleanup. Collect a short confirmation list for the end, and **keep those
comments in place while you ask**, because a wrong deletion is the only irreversible mistake
available here:

- A "why" you cannot corroborate from the code — an outage, a customer, a decision made
  somewhere you cannot see.
- A TODO or FIXME that looks done, or old enough that you cannot tell.
- Comment and code contradicting each other in a way that smells like a bug. Do not delete
  the comment to resolve it — it may be the only witness. Report it separately.
- A convention you would be breaking project-wide (file headers on every file, banner style).
- A file where you would remove most of the comments — say what you'd remove and why before
  doing it.

## 4 — Make the edits

One file at a time, comments only.

- A line that held nothing but a comment goes away entirely; do not leave a blank line where
  it was. If a removal leaves two or more consecutive blank lines, collapse them to one —
  that is the only whitespace change permitted.
- A trailing comment leaves with the whitespace in front of it: `x = 1  # why` → `x = 1`.
- Do not reflow, reindent, reorder, or reformat code, sort imports, or fix a typo in an
  identifier. Not one character.

## 5 — Prove the code is untouched

```bash
python3 <skill>/scripts/code_guard.py check <scratch>/comment-gc-snapshot
```

The guard strips comments and collapses whitespace outside string literals, then compares
what is left; Python goes through the AST, so docstring edits are allowed while every other
literal is still compared exactly.

| Verdict | What it means | What to do |
|---|---|---|
| `OK` | Code identical | Nothing |
| `LIMITED` | Verified, but the language is only partly understood | Read that file's diff yourself |
| `CHANGED` | Code differs | `code_guard.py restore <snap> <file>`, then redo the file |
| `SKIPPED` | Language unknown to the guard | Either revert the file or verify by hand and say so in the report |

Never report a `CHANGED` file as done, and never explain it away — the mechanical check is
the promise this skill makes. If the guard also prints "changed lines outside any comment",
look at each one; usually it is an indentation slip.

Then read `git diff` once yourself. The guard proves you changed no code; only you can
notice that you deleted a comment you should have kept.

## 6 — Report

A receipt, not a document. Write it in the language the user wrote to you in — the
template below is only a shape.

```markdown
## Comment GC — <scope, e.g. 7 files on feature/checkout>

| File | Deleted | Compressed | Kept |
|---|---|---|---|
| src/checkout/pay.ts | 12 | 3 | 5 |
| src/checkout/cart.ts | 4 | 1 | 9 |

**Notable removals**
- `pay.ts` — four comments narrating a refactor from an earlier session.
- `cart.ts` — a commented-out fallback path, superseded two commits ago.

**Left for you to decide** (kept as-is)
1. `pay.ts:88` — "expiry cases are special-cased at the payments team's request" — nothing
   in the code corroborates this. Delete it, or move it to an ADR?
2. `cart.ts:12` — `TODO(CART-88): remove after migration`; the migration looks finished.

**Possible bug** — `cart.ts:140` says quantities are capped at 99, the code caps at 999.
Left both alone.

Verified: 7 files `OK`, 1 `LIMITED` (index.html, read the diff), 0 changed.
```

Skip any section that is empty. If you cleaned nothing, the report is one sentence.

## What makes this skill fail

- Editing code "while you're in there". The one thing it promises not to do.
- Deleting a comment because it is long. Length is not the crime; irrelevance is.
- Rewriting surviving comments into a house voice. You are removing noise, not imposing style.
- Inventing work in a file whose comments were already fine.
- Reaching outside the resolved scope because a nearby file looked messy. Mention it instead.
